# Best Practices: Prompt Verifier

## Правила проектирования инструкций

### R1: Каждый запрет требует обоснования

Правило: добавлять «почему» к каждому `никогда`, `не делай`, `запрещено`.

Обоснование: обоснование превращает одно правило в систему поведения. Агент, понимающий «почему нельзя force push» — автоматически избежит `git reset --hard origin/main` без отдельного правила.

Формула: `Никогда не используйте X — [последствие]. Вместо этого используйте Y.`

### R2: Максимум 3 уровня заголовков (h1/h2/h3)

Правило: h4 и глубже — сигнал к рефакторингу структуры или вынесению в отдельный файл.

Обоснование: глубокая вложенность создаёт неопределённость — какой уровень главный? В плоских структурах все инструкции на поверхности.

### R3: Описательные имена файлов

Правило: имя файла должно описывать содержимое без открытия файла.

Хорошие примеры: `api-authentication.md`, `deployment-checklist.md`, `setup-local-dev.sh`

Плохие примеры: `guide.md`, `notes.md`, `setup.sh`

### R4: Заголовок для каждой темы

Правило: один заголовок на одну тему. Абзацы прозы без заголовков конкурируют за внимание агента.

### R5: Команды — только в блоках кода

Правило: команда в прозе — это описание. Команда в `backticks` — это инструкция к выполнению.

Приоритет: если применить только одно правило — выбрать R5. Наибольший эффект на соблюдение агентом.

### R6: Стандартные имена разделов

Эталонные имена: `## Testing`, `## Commands`, `## Structure`, `## Conventions`, `## Setup`, `## Usage`, `## Errors`, `## Input`, `## Output`, `## CI`

Принцип: знакомое имя = сигнал. Креативное имя = шум.

### R7: Тест «выполни немедленно»

Правило: каждая инструкция должна пройти тест — «Может ли агент выполнить это прямо сейчас, не задавая уточняющих вопросов?»

Если нет — это пожелание, не инструкция. Переписать до конкретного действия.

## Типичные ловушки

### Ловушка 1: «Я добавлю больше слов и агент поймёт»

Проблема: добавление слов к расплывчатой инструкции не делает её выполнимой.

Последствие: инструкция становится длиннее, но по-прежнему не проходит тест R7.

Решение: не добавлять слова — переформулировать в конкретное действие.

### Ловушка 2: Блок кода без контекста раздела

Проблема: `pytest` в блоке кода в середине прозового абзаца без заголовка секции.

Последствие: команда видна, но агент не знает когда её запускать (R4 + R6 нарушены).

Решение: `## Testing` → `` `pytest` `` — запуск из корня перед коммитом

### Ловушка 3: Обоснование как отдельный абзац

Проблема: правило в одном месте, обоснование — в другом разделе.

Последствие: агент читает правило без контекста, обоснование теряется.

Решение: обоснование — inline, сразу после запрета, через тире.

### Ловушка 4: rules_focus без финального полного прохода

Проблема: использование `rules_focus` для целевой проверки, но не делая полный прогон перед релизом.

Последствие: пропущенные нарушения других правил накапливаются.

Решение: финальный прогон без `rules_focus` перед мержем в main.

## Советы по производительности

### Совет 1: Начинать с R5 (команды в блоках кода)

Самое быстрое исправление с наибольшим эффектом. Один проход `Ctrl+F` по документу находит все команды в прозе.

Эффект: агент начинает выполнять инструкции стабильнее уже после первого сеанса.

### Совет 2: R6 как структурный скелет

Сначала выставить стандартные заголовки разделов, затем заполнять содержимое. Структура → содержание, не наоборот.

Эффект: автоматически решает часть нарушений R4 (каждая тема получает заголовок).

### Совет 3: Использовать режим `verify` для code review CLAUDE.md в PR

Запустить `prompt-verifier` в режиме `verify` на diff изменений CLAUDE.md в pull request — быстрый аудит без полной адаптации.

Эффект: предотвращает регрессии качества инструкций при командной работе.

### Совет 4: Длина — потолок, структура — сигнал

Не оценивать качество CLAUDE.md по длине. 20-строчный абзац без заголовков хуже 60-строчного структурированного документа.

Метрика: score/7 важнее word count.
