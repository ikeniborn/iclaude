Исследование: Улучшение маскирования секретов в PreToolUse hook¶

Дата: 2025-02-25 Тип исследования: Security Analysis & Feature Enhancement Статус: Завершено

Резюме¶

Проведено комплексное исследование возможностей улучшения качества маскирования секретов в PreToolUse hook redact-secrets.py для Claude Code. Анализ включал:

  1. Актуальные форматы API токенов (2025-2026) — изучены форматы 14+ крупных провайдеров

  2. Паттерны из популярных инструментов — проанализированы gitleaks, trufflehog, detect-secrets

  3. Риски false positives — выявлено 11 категорий риска маскирования легитимных данных

  4. Анализ производительности regex — найдены 4 потенциальные проблемы ReDoS

  5. Рекомендации по архитектуре — предложена модульная архитектура с конфигурационными файлами

Ключевые Находки¶

2. Риски False Positives¶

Выявлено 11 категорий риска:

  1. UUIDs в конфигах — может маскировать project_id, user_id как секреты

  2. Bash плейсхолдеры — ${VAR_NAME} частично защищены, но не полностью

  3. Base64 строки — JWT паттерн может ловить легитимный base64 в логах

  4. Docker образы — gcr.io/project/image@sha256:hash может восприниматься как токен

  5. URL параметры — слишком жадное совпадение в URL credentials

  6. Git хеши — hex строки 32+ символов похожи на токены

  7. Версии пакетов — v1.2.3-abc123xyz может ловиться как токен

  8. Тестовые пароли — test_password = "Test@123" в тестовом коде

  9. Configuration templates — {{ default_password }} Ansible variables

  10. SQL запросы — UUIDs в WHERE условиях

  11. Очень длинные значения — может быть медленным на больших текстах

Рекомендация: Требовать контекст переменной для generic patterns (secret=, token=, api_key=)

3. Проблемы Производительности Regex¶

Найдено 4 потенциальные проблемы ReDoS (Regular Expression Denial of Service):

Паттерн

Проблема

Пример

Решение

[\s\S]*? без лимита

Ограничить до 5000 символов

[^@\s/]+ жадно

Статус производительности: 🟡 ХОРОШАЯ, но требует усиления

4. Архитектурные проблемы¶

Текущая архитектура: Монолитная, хардкод паттернов в Python коде

Проблемы:

  • Нельзя обновлять паттерны без изменения основного кода

  • Нет версионирования паттернов

  • Отсутствует тестовый фреймворк для regression tests

  • Нет логирования какие паттерны работают/не работают

  • Нет механизма для исключения файлов от маскирования

Рекомендуемая архитектура: Внешний конфиг JSON с паттернами

.claude-isolated/hooks/
├── redact-secrets.py          (основной скрипт, минимальная логика)
├── loader.py                  (загрузчик паттернов из patterns.json)
├── redactor.py                (основная логика маскирования)
├── patterns.json              (актуальные паттерны)
├── patterns.schema.json       (JSON Schema для валидации)
└── tests/
    ├── test_patterns.py
    ├── test_false_positives.py
    └── fixtures/

Конкретные Рекомендации¶

Priority 1: Критические улучшения¶

# Добавить в REDACT_PATTERNS:

# 1. Google AI Studio
(
    re.compile(r'\bAIzaSy[A-Za-z0-9_-]{32}\b'),
    '[GOOGLE_API_KEY]',
    'Google AI Studio (Gemini) API key',
),

# 2. Stripe API Keys
(
    re.compile(r'\b(?:sk|pk)_(?:live|test)_[A-Za-z0-9]{20,}\b'),
    '[STRIPE_API_KEY]',
    'Stripe API key (secret or publishable)',
),

# 3. HuggingFace Token
(
    re.compile(r'\bhf_[A-Za-z0-9_]{30,}\b'),
    '[HUGGINGFACE_TOKEN]',
    'Hugging Face User Access Token',
),

# 4. OpenRouter API Key
(
    re.compile(r'\bsk-or-[A-Za-z0-9\-_]{50,}\b'),
    '[OPENROUTER_API_KEY]',
    'OpenRouter API key',
),

# 5. Groq API Key
(
    re.compile(r'\bgsk_[A-Za-z0-9\-_]{50,}\b'),
    '[GROQ_API_KEY]',
    'Groq API key',
),

Priority 2: Исправления проблем производительности¶

# Улучшить существующие паттерны с максимальными длинами:

# PEM private key - ограничить до 5000 символов
(
    re.compile(
        r'-----BEGIN (?:RSA |EC |DSA |OPENSSH )?PRIVATE KEY-----'
        r'[\s\S]{0,5000}?'  # Добавить лимит
        r'-----END (?:RSA |EC |DSA |OPENSSH )?PRIVATE KEY-----'
    ),
    ...
),

# URL credentials - ограничить пароль до 100 символов
(
    re.compile(r'((?:https?|ftp|postgresql|mysql|mongodb|redis)://)[^:@\s/]{1,100}:[^@\s/]{1,100}@'),
    ...
),

# Generic secret - ограничить до 256 символов
(
    re.compile(
        r'(?i)((?:secret|api[_\-]?key|access[_\-]?token|auth[_\-]?token)'
        r'\s*[=:]\s*)["\']([A-Za-z0-9\-_./+]{16,256})["\']'  # Добавить макс
    ),
    ...
),

Priority 3: Рефакторинг архитектуры¶

  1. Вынести паттерны в patterns.json — шаблон предоставлен в patterns.json.example

  2. Создать loader.py — для загрузки и валидации паттернов из JSON

  3. Добавить tests/ — pytest тесты для regression testing

  4. Добавить .redact-ignore — механизм исключения файлов от маскирования

  5. Добавить логирование — JSON логирование найденных типов секретов

Заключение¶

Текущий hook redact-secrets.py обеспечивает хорошую базовую защиту (~45% провайдеров), но имеет ряд возможностей для улучшения:

✅ Сильные стороны:

  • Хороший дизайн с fail-open политикой

  • Защита от большинства известных форматов

  • Низкие риски false positives для существующих паттернов

⚠️ Потенциальные проблемы:

  • Недостаточное покрытие новых провайдеров (Google AI, Stripe, Groq и т.д.)

  • Возможные проблемы ReDoS на больших текстах

  • Сложность расширения без изменения основного кода

🎯 Рекомендация: Приоритизировать добавление критических новых форматов (Priority 1) и переход на конфигурационный подход для долгосрочной масштабируемости.
