# Design: result-only HTML report for the IDD→SDD chain

**Date:** 2026-07-10
**Topic:** `result-only-html-report`
**Status:** draft
**Scope:** stop generating the chain HTML report at the `intent` / `spec` / `plan`
stages; generate a single implementation-focused report only at the `result` stage.
Retire the `mode: chain` machinery in the `html-report` skill. Edits touch
`skills/check-chain/SKILL.md`, `skills/html-report/SKILL.md`,
`skills/html-report/references/chain-report.md` (deleted),
`skills/html-report/references/dynamics.md`, and the `iclaude`
iwiki page `idd-chain-validation.md`.

## 1. Problem

`check-chain` Step 5 ("HTML report") is part of the **shared core** — it runs on
**every** stage (`intent`, `spec`, `plan`, `result`). Each stage invokes the
`html-report` skill with `mode: chain`, `tab: <stage>`, and merges its own tab into
a single four-tab file `docs/superpowers/reports/<topic>-results.html`, preserving
the other three tabs verbatim.

This has two costs:

1. **Report churn on every stage.** An HTML artifact is produced/rewritten four
   times per chain, even though the intent / spec / plan tabs restate validation
   findings that are already reported in the chat and stored in frontmatter. The
   report becomes noise generated at the wrong moments (before any code exists).
2. **A whole `mode: chain` subsystem exists only for this.** `grep` confirms
   `mode: chain` is called from nowhere but `check-chain` — a four-tab merge
   engine, boundary-marker contract, `references/chain-report.md`, and dedicated
   self-validation / autonomy-zone rows in `html-report`, all serving one caller.

The user wants the report to describe the **outcome of the implementation**, formed
once, at the end — not the state of each validation stage.

## 2. Goals / Non-goals

**Goals**
- Generate the HTML report **only** at the `result` stage, and only when there is a
  non-empty `git diff` (a real implementation to report on).
- Make the report a single-page, implementation-focused artifact: what changed,
  the results (plan↔diff reconciliation, intent/spec coverage), the impact of the
  change, and diagrams **when the change is structural**.
- Remove the `mode: chain` machinery from `html-report` entirely (dead code after
  this change): the code path, `references/chain-report.md`, the chain-only
  self-validation checklist items, the chain autonomy-zone wording, and the pointer
  from `references/dynamics.md`.
- Keep `intent` / `spec` / `plan` validation behaviour intact minus the HTML: the
  phase loop, findings, verdicts, `review:` frontmatter, and the `docs/TODO.md`
  upsert are unchanged.

**Non-goals**
- Changing any phase checklist, severity, or the hashing algorithm.
- Changing the `chain-gate.py` hook or `settings.json` — the hook communicates only
  through artifact frontmatter and never touches the HTML report.
- Migrating existing four-tab `<topic>-results.html` files on disk — they are
  historical; the new single-page report simply overwrites the same path on the
  next `result` run for that topic.
- Changing the report's output path or filename
  (`docs/superpowers/reports/<topic>-results.html` is kept).

## 3. Architecture

### 3.1 `check-chain` — Step 5 becomes result-only

Today Step 5 sits in the **Shared core** section ("applied by every stage"). Move it
out of the shared core so it applies to the `result` stage only. Concretely:

- The shared-core Step list keeps Steps 0–4 (quick-exit, scope, init, phases,
  verdict) and Step 6 (TODO upsert) for all stages. Step 5 (HTML report) is
  re-scoped to `result` and its content contract is rewritten (§3.2).
- Every "HTML tab" mention in the run-mode descriptions is updated:
  - Whole-chain mode: stages `intent` / `spec` / `plan` run "Step 1–4 + Step 6"
    (findings → verdicts → frontmatter → TODO cell), with **no HTML**. Only the
    `result` stage additionally runs Step 5.
  - Single-stage mode: same — `/check-chain intent|spec|plan` produces no HTML;
    `/check-chain result` produces the report.
- The empty-diff path is unchanged: `result` reached with an empty `git diff` emits
  INFO «result pending implementation» and produces **no** report (there is nothing
  to report yet).

### 3.2 New `result` report content contract

The report is generated by the `html-report` skill in its **default `standalone`
mode** (not `mode: chain`), written to the explicit caller-supplied path
`docs/superpowers/reports/<topic>-results.html`. An explicit caller path is the
`html-report` **Full** autonomy zone, so the file is created / overwritten (whole
regeneration) without a prompt.

The report is one self-contained page with these sections (all text in Russian):

1. **Резюме внедрения** — topic; links to the chain docs (intent / spec / plan
   paths); the diff base (`HEAD`, or `<ref>` when `--since=<ref>` was passed).
2. **Выполненные изменения** — a per-file table: path, change kind
   (added / modified / deleted), ± lines, and a one-line description of what the
   change does. Derived from the `git diff` already computed in the `result`
   reconciliation.
3. **Результаты** — the plan↔diff reconciliation already produced by the `result`
   stage: per-step status (DONE / PARTIAL / MISSING) with diff evidence; intent
   Desired-Outcomes coverage N/M; spec requirements coverage N/M; excess changes
   (files changed with no matching plan step); the final verdict.
4. **Влияние на систему** — a table of what the change affects: components / files
   touched, behavioural changes, and risks or follow-ups. Sourced from the diff and
   the intent's stated outcomes.
5. **Схемы** *(conditional — see §3.3)* — architecture / change-flow and/or an
   impact map, using the `html-report` diagram grammar (CSS block/flow + C4 from
   `references/css-diagrams.md`; SVG node-edge graphs for looping / non-adjacent
   edges from `references/svg-diagrams.md`).

The report explains the implementation outcome; it is not a bare findings dump.
Sections 1–4 are always present. Section 5 appears only when the diagram trigger
fires.

### 3.3 Diagram trigger (conditional)

Include diagrams in section 5 when the change is **structural** — i.e. the diff
does at least one of:

- adds a new module / file / component (a new source file, a new public
  function/class that other code will call), OR
- adds or changes dependency edges between components (new import/require wiring, a
  changed call graph between modules), OR
- introduces a new data-flow / control-flow / state machine.

Otherwise (a point bugfix, a text/comment/config tweak, or edits contained within
existing files with no new cross-component wiring) → tables only, no diagram.

These criteria are written into the `check-chain` `result` Step 5 as an explicit,
closed checklist the skill evaluates against the diff, so the decision is
deterministic rather than a judgement call.

### 3.4 `html-report` — remove `mode: chain`

`mode: chain` is dead after §3.1. Remove it from `skills/html-report/SKILL.md`:

- The `mode: chain` note in Hard Constraint 5 (output directory) and the workflow
  Step 3 recipe pointer / Step 6 merge-flow paragraph.
- The chain-only block of the Self-Validation checklist (the four
  `TAB:{intent,spec,plan,result}` / tab-radio / theme-toggle / non-owned-pane
  items).
- The chain wording in the Autonomy-Zones "Full" row (the "including merging one
  tab into an existing caller-supplied `mode: chain` file" clause).
- Delete `skills/html-report/references/chain-report.md`.
- Remove the chain-report pointer in `skills/html-report/references/dynamics.md`
  (the "Full IDD→SDD chain-report merge contract … → `chain-report.md`" line).

The default `standalone` behaviour, the zero-dependency / offline / both-themes
constraints, and every other reference file are untouched.

### 3.5 Wiki

Update the `iclaude` iwiki page `idd-chain-validation.md`: the "HTML report content
contract (Step 5)" section (which documents the four-tab per-stage contract) is
rewritten to describe the result-only single-page report; the Overview and
`check-chain` sections' mentions of the per-stage HTML tab are corrected. Use
`wiki_update_page` per changed source.

## 4. Data flow

```
/check-chain intent|spec|plan   → Steps 0–4, 6 → findings (chat) + review: frontmatter + TODO cell   [NO HTML]
/check-chain result (empty diff) → INFO «result pending», TODO Result cell «–»                        [NO HTML]
/check-chain result (diff)       → reconcile plan↔diff + intent/spec coverage
                                   → result_check: frontmatter + TODO close
                                   → Step 5: html-report (standalone) → docs/superpowers/reports/<topic>-results.html
                                       sections 1–4 always; section 5 (diagrams) iff structural-change trigger fires
```

## 5. Testing / Verification

1. **Dead-code sweep:** `grep -rn "mode: chain\|chain-report" skills/` returns
   nothing (the historical `.claude.json` state entries and the memory note are out
   of scope and may still match — they are not skill code).
   `test ! -f skills/html-report/references/chain-report.md`.
2. **No HTML on upstream stages:** run `/check-chain intent` (or `spec` / `plan`) on
   a test topic → confirm the stage still reports findings, writes `review:`
   frontmatter, and upserts the TODO cell, and that **no** `<topic>-results.html` is
   created or modified.
3. **Report on result:** run `/check-chain result` with a non-empty `git diff` →
   confirm a single-page `<topic>-results.html` is written with sections 1–4, all
   text in Russian.
4. **Conditional diagram:** with a structural diff (a new file / new cross-module
   wiring) → section 5 with a diagram is present; with a point-fix diff → section 5
   is absent.
5. **Empty-diff path:** `/check-chain result` on an empty diff → INFO «result
   pending», no report file.
6. **`html-report` self-validation:** the produced report passes the standalone
   checklist — zero external `src=`/`href=`, both theme palettes + toggle, single
   `.html`, ≤ 5 MB.
