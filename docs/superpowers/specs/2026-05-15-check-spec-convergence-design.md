# Check-Spec / Check-Plan: сходимость проверок

**Дата:** 2026-05-15
**Автор:** brainstorming session
**Статус:** draft

## Проблема

Команды `/check-spec` и `/check-plan` при повторных прогонах постоянно находят новые замечания вместо схождения к стабильному «OK». Симптомы:

- Новые `[WARNING]` неоднозначности и стилевые правки на каждом проходе
- Новые `[CRITICAL]` пропуски покрытия, которых «не было» раньше
- Новые структурные находки (TODO, битые ссылки) после правок
- Те же замечания возвращаются в другой формулировке

## Корневые причины

1. **Слои смешаны.** Один проход покрывает структуру + покрытие + ясность + стиль. LLM непроизвольно выбирает разный срез каждый раз → видимость новых находок.
2. **Нет state.** Команда не помнит, какие замечания были приняты, отклонены или исправлены. Принятые возвращаются.
3. **Нет хеш-привязки.** Правка одной фразы рождает каскад «новых» находок в соседних местах — без понимания, что изменилась только одна секция.
4. **Нет машинного exit-критерия.** Вердикт «Чисто: OK» субъективен. Не существует условия, при котором команда обязана остановиться.

## Архитектура решения

Одна команда `/check-spec`, четыре строго последовательные ортогональные фазы, state во frontmatter самой спеки, exit по хешу + закрытым вердиктам.

Та же модель применяется к `/check-plan` симметрично (фазы другие, механика идентична).

### Фазы check-spec

| # | Фаза | Чек-лист (закрытый список) | Не проверяет |
|---|------|-----------------------------|--------------|
| 1 | **structure** | плейсхолдеры (TODO/TBD/???), битые внутренние ссылки, нумерация разделов, дубли секций | смысл, покрытие, стиль |
| 2 | **coverage** | каждая задача покрыта ≥1 требованием; каждое требование привязано к задаче; противоречия между требованиями | стиль, формулировки |
| 3 | **clarity** | неоднозначные формулировки («быстро», «удобно» без критерия); требования без DoD; несогласованные термины | покрытие, структуру |
| 4 | **consistency** | сверка ранее approved секций по хешу; повторных поисков не делает | новые поиски |

### Фазы check-plan

| # | Фаза | Чек-лист | Не проверяет |
|---|------|----------|--------------|
| 1 | **structure** | плейсхолдеры, нумерация шагов, дубли шагов | покрытие, зависимости |
| 2 | **coverage** | каждое требование спеки покрыто шагом; лишние шаги без требования | зависимости, формулировки |
| 3 | **dependencies** | порядок шагов корректен; нет циклов; результаты предыдущих шагов доступны последующим | стиль |
| 4 | **verifiability** | у каждого шага измеримый критерий готовности | покрытие |
| 5 | **consistency** | сверка approved секций по хешу | новые поиски |

### Правила перехода между фазами

- Фаза N+1 стартует только если в фазе N: `count(severity=CRITICAL, verdict=open) == 0`
- WARNING не блокирует переход, но финальный OK требует verdict у всех WARNING
- Каждая фаза имеет закрытый список проверок — LLM не может расширить набор. Это убивает non-determinism.

## State во frontmatter спеки и плана

```yaml
---
review:
  spec_hash: sha256:abc123...           # хеш тела документа без frontmatter
  last_run: 2026-05-15
  phases:
    structure:    { status: passed,  finished: 2026-05-15 }
    coverage:     { status: passed,  finished: 2026-05-15 }
    clarity:      { status: in_progress }
    consistency:  { status: pending }
  findings:
    - id: F-001
      phase: clarity
      severity: WARNING
      section: §3.2
      section_hash: sha256:def456...    # хеш текущего тела секции
      text: "«быстро» без критерия измерения"
      verdict: accepted                 # open | accepted | wontfix | fixed
      verdict_at: 2026-05-15
---
```

### Семантика полей

- `spec_hash` — sha256 тела документа (frontmatter исключён). Сравнивается при старте: если совпал и все verdicts закрыты — мгновенный OK без LLM.
- `phases[*].status` — `pending | in_progress | passed`. Только `passed` всех фаз даёт право на OK.
- `findings[].id` — стабильный идентификатор формата `F-NNN`, монотонно растёт. Повторный прогон фазы видит существующие id+text → не дублирует, добавляет только новое.
- `findings[].section_hash` — хеш только той секции, к которой привязано замечание. При правке секции `verdict` всех её findings сбрасывается в `open` (точечно, не вся спека).
- `findings[].verdict`:
  - `open` — требует решения пользователя
  - `accepted` — пользователь согласен с замечанием, оставляет как есть (например, «быстро» допустимо в контексте)
  - `wontfix` — отклонено как неактуальное
  - `fixed` — исправлено в тексте (хеш секции должен подтверждать изменение; иначе verdict невалиден)

## Exit-критерий

Команда выдаёт `OK` тогда и только тогда, когда выполнены ВСЕ условия:

```
current_spec_hash == frontmatter.review.spec_hash
∧ ∀ phase ∈ phases: phase.status == passed
∧ ∀ finding ∈ findings: finding.verdict ∈ {accepted, wontfix, fixed}
∧ count(severity == CRITICAL ∧ verdict == open) == 0
```

При совпавшем хеше и закрытых вердиктах команда выводит `OK (cached, hash match)` и не запускает LLM вообще — это и есть лекарство от «бесконечных новых замечаний».

## Канонический алгоритм хеширования

Без единого алгоритма сходимости не будет: frontmatter живой, меняется каждый прогон. Реализация ОБЯЗАНА считать хеш ОДИНАКОВО.

- **Хеш тела документа** (исключает frontmatter):
  ```bash
  awk 'BEGIN{fm=0} /^---$/{fm++; next} fm>=2{print}' <FILE> | sha256sum | cut -c1-16
  ```
- **Хеш секции** — тело секции от заголовка `##`/`###` до следующего заголовка того же или более высокого уровня (не включая его), пропущенное через `sha256sum | cut -c1-16`.
- Если frontmatter отсутствует (счётчик `---` не достиг 2) — хеш всего файла: `sha256sum <FILE> | cut -c1-16`.

Команда обязана вызывать эти bash-команды через инструмент Bash. Хеши «в уме» запрещены.

## Изменённый алгоритм команды

### Шаг 0. Quick exit по state
1. Прочитать frontmatter.review (если есть)
2. Посчитать текущий `spec_hash` по каноническому алгоритму
3. Если `current_hash == frontmatter.spec_hash` И все exit-условия выполнены → вывести `OK (cached)` и выйти

### Шаг 1. Определить scope
(существующая логика поиска файла спецификации)

### Шаг 2. Подтвердить файл и инициализировать state
1. Подтвердить путь у пользователя
2. Если frontmatter отсутствует — инициализировать пустой `review:` блок
3. Посчитать хеши всех секций. Для каждого существующего finding с `section_hash != current_section_hash` — сбросить verdict в `open`. Зафиксировать `spec_hash`.

### Шаг 3. Выполнение фаз
Для каждой фазы в фиксированном порядке (`structure → coverage → clarity → consistency`):

1. Прочитать список существующих findings этой фазы со статусом `open` или новыми хешами
2. Применить закрытый чек-лист фазы к спеке
3. Для каждой новой находки: присвоить id `F-NNN`, записать `section_hash`, добавить во frontmatter с `verdict: open`
4. Существующие findings с тем же section_hash и тем же текстом — НЕ дублировать
5. Вывести отчёт по фазе пользователю
6. Дождаться вердиктов пользователя по новым findings (если есть CRITICAL — обязательно; WARNING — желательно)
7. Записать verdicts во frontmatter
8. Если в фазе нет CRITICAL с `verdict=open` → `phase.status = passed`, переход к следующей; иначе — `in_progress`, остановка с просьбой исправить

### Шаг 4. Финальный вердикт
Применить exit-критерий. Вывод: `OK` либо `требует доработки: N critical open, M warning open`.

## Запреты (без изменений)

- Придумывать задачи/требования, которых нет в исходном описании
- Редактировать содержимое спецификации/плана без явного запроса (frontmatter — исключение, обновляется командой)
- Писать «вероятно подразумевается» без ссылки на текст

## Совместимость

- Старые спеки без frontmatter получают пустой `review:` блок при первом запуске
- Существующие frontmatter с другими полями (например, `name:`, `description:`) сохраняются, добавляется только `review:`
- Откат: удаление `review:` блока возвращает поведение к ручной проверке
